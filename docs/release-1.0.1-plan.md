# Safe Ride Bicycle 1.0.1 작업 지시서

## 0. 공통 규칙 (모든 작업에 적용)

### 진행 방식
- 브랜치: `main`에서 `release/1.0.1` 생성 후 이 브랜치에서만 작업
- 모든 작업은 **조사 → 보고 → 내 승인 → 구현** 순서. 승인 전에는 코드·DB를 수정하지 말 것
- 작업(A1, A2 …)마다 별도 커밋. 커밋 전 diff를 보여주고 내 승인을 받을 것
- 한 번에 한 작업만 진행. 여러 작업을 섞지 말 것

### DB 작업 규칙
- 운영 DB는 저장소와 다를 수 있음. 수정 전 운영 실제 상태를 확인할 것
  (pg_policies, pg_get_functiondef 등 확인 쿼리를 **작성만** 하고, 실행은 내가 함)
- 적용 순서: 스테이징(safe-ride-staging, ref okixksradpfzspbticia) → 운영(samrt-rider-DB, ref jidpwflthppsltdayhoy)
- 마이그레이션은 `supabase/migrations/YYYYMMDD_설명.sql`, 테스트는 `supabase/tests/`
- 신규 테이블은 RLS 활성화 + 필요한 권한만 명시 GRANT (CLAUDE.md 규칙)
- 모든 쓰기는 SECURITY DEFINER RPC로만. 테이블 직접 쓰기 권한을 새로 열지 말 것

### 하위 호환 (중요)
- 스토어의 1.0(4) 앱은 1.0.1 출시 후에도 한동안 사용됨
- **서버 변경은 1.0(4) 앱을 깨뜨리면 안 됨.** 기존 컬럼·RPC를 제거하거나 동작을 바꾸는 변경은

## A. 서버 작업 (재심사 불필요, 앱 출시 전 적용 가능)

### A1. expire_stale_zones 자동 실행 (cron)

**조사 (수정 금지)**
1. 저장소의 함수 정의와, 운영 정의 확인용 쿼리
2. 만료 기준: 상태별(미확정/확정) 조건, 기준 컬럼과 기간, 삭제인지 상태 변경인지, 연관 reports 처리
3. 만료 시 신고자 벌점·신뢰도 등 profiles에 영향을 주는 로직 유무
4. 상황실(admin.html)과 앱에서 호출하는 위치
5. 첫 실행 시 만료될 마커 수를 미리 세는 SELECT 쿼리 (운영 마커 약 128개 대상)
6. 기존 cron `purge-stale-emergency-logs`(매일 03:20 UTC)와의 시간 충돌, submit_hazard_report의 advisory lock과 동시 실행 시 문제
7. 적절한 실행 주기 제안

**구현 (승인 후)**
- 3번에서 벌점 로직이 있으면, 만료로 인한 벌점은 적용하지 않도록 먼저 수정 제안
- pg_cron 등록 마이그레이션 + 스테이징 테스트 시나리오

### A2. 상황실에서 미확정 마커를 관리자가 확정하는 기능

**목적**: 초기 사용자 참여가 적어 두 번째 신고가 들어오기 어려움. 운영자가 라이딩으로 직접 확인한 위험 구역을
상황실에서 확정 처리해 지도에 진하게 표시되도록 함. 운영자 본인 신고와 일반 사용자 신고 모두 대상.

**조사 (수정 금지)**
1. 마커의 확정/미확정 표시가 zones의 상태값으로 서버에서 결정되는지, 앱이 신고 수 등으로 계산하는지
   (api.js, CONF_STYLE 관련 코드). 앱이 계산한다면 앱 수정 범위도 보고
2. 상황실 현황: 마커 조회·관리 화면 구조, Render 서버 경유 service_role 호출 경로
3. **상황실 접근 제한 방식** (로그인·인증이 있는지, 누구나 URL로 접근 가능한지). 부족하면 보완안 제시
4. A1의 만료 로직, 벌점 로직에 관리자 확정 마커가 어떻게 영향받는지

**구현 요구사항 (승인 후)**
- zones에 확정 기록 추가: 관리자 확정 여부, 확정 시각 (컬럼명·타입은 제안받아 결정)
- 확정 처리는 service_role만 호출 가능한 RPC 또는 서버 경로로. anon/authenticated에는 권한 주지 말 것
- 상황실 UI: 미확정 마커 목록/지도에서 선택 → 확정 버튼 → 확인 대화상자 → 확정
- 확정 해제(되돌리기) 기능도 함께 (실수 대비)
- 관리자가 확정한 마커는 벌점 로직에서 신고자 불이익이 생기지 않도록
- 만료 정책: 관리자 확정 마커도 일반 확정 마커와 같은 만료 규칙 적용(별도 예외 없음)
- 기존 운영 마커(약 128개)를 상황실에서 하나씩 검토·확정할 수 있으면 됨. 일괄 확정 SQL은 만들지 말 것
- 가능하면 앱 수정 없이 DB + 상황실 변경만으로 완료. 불가능하면 이유와 앱 수정 범위를 먼저 보고

### A3. 비밀번호 정책 (서버 설정은 내가 직접 함)
- 정책: 최소 8자, 영문 + 숫자 포함 (특수문자 강제 없음)
- Supabase 대시보드 설정은 내가 **1.0.1 출시 시점에** 직접 변경함. 코드 작업은 B1에서 앱 쪽 대응만

## B. 앱 작업 (1.0.1 빌드, 재심사 필요)

배경: App Store 사용자 피드백 반영

### B0. 조사 (수정 금지, B1~B4 전체 대상)
1. 로그인/가입 화면 구조, 가입 성공 후 화면 전환 로직
2. 이메일 인증 전 상태에서 앱 동작 (세션 유무, 신고 가능 여부)
3. 이미 가입된 이메일로 signUp 시 응답 처리 (`data.user.identities`가 빈 배열인지 확인하는 코드 유무)
4. Supabase 인증 에러 메시지를 그대로 표시하는지, 한글로 변환하는지
5. 가입 성공·탭 전환 후 입력값(특히 비밀번호)이 남는 원인
6. 이메일/비밀번호 input의 type, autocomplete 속성 현황
7. "로그인 정보 저장"이 무엇을 어디에 저장하는지. **비밀번호를 localStorage 등에 저장하고 있으면 최우선 보고**
8. 모달(사용자 정보, 설정, 위험 구역 보기) 구현 방식과 드래그 닫기 로직, 내부 스크롤과 충돌하는 원인
9. zones.reporter_ids를 앱이 어디서 쓰는지 (api.js:59 차단 필터 포함)

### B1. 인증 흐름 개선
- 가입 완료 후 로그인된 것처럼 넘어가지 않게: "인증 메일을 보냈습니다. 메일 확인 후 로그인해 주세요" 안내 → 로그인 화면
- 이미 가입된 이메일: "이미 가입된 이메일입니다" 안내
- 인증 에러 메시지 한글 변환 (비밀번호 정책 위반, 잘못된 로그인, 미인증 이메일, 네트워크 오류 등)
- 비밀번호 입력 시 조건 안내 문구 + 클라이언트 검증 (최소 8자, 영문+숫자). 서버 정책과 동일하게
- 화면 구조: 탭 대신 "로그인 화면 + 하단 '계정이 없으신가요? 가입하기'" 구조로 변경 제안 (B0 결과 보고 결정)

### B2. 폼 상태와 로그인 정보 저장
- 가입 성공, 화면 전환 시 입력값 초기화 (비밀번호 필드는 항상 비움)
- input 속성: 로그인 이메일 `autocomplete="username"`, 로그인 비밀번호 `current-password`,
  가입 비밀번호 `new-password` → iOS 키체인 저장·자동완성이 동작하도록
- 앱이 비밀번호를 직접 저장하는 기능이 있다면 제거. 필요하면 "이메일 저장" 체크박스만 제공
- 로그인 유지(세션)는 현재 동작 유지

### B3. 모달 스크롤/닫기
- 대상: 사용자 정보, 설정, 위험 구역 보기 모달
- 동작: 내용이 맨 위일 때만 아래로 당기면 닫힘, 그 외에는 내부 스크롤. 상단 핸들 영역은 항상 드래그 닫기 가능
- 세 모달에 공통 적용 가능한 구조로

### B4. zones.reporter_ids 노출 제거 (하위 호환 2단계)
- 1단계(1.0.1과 함께): `get_visible_zones` RPC 추가, 앱이 이 RPC를 쓰도록 전환.
  RPC는 reporter_ids 대신 필요한 정보만 반환 (예: 현재 사용자의 신고 여부 boolean)
- 2단계(1.0.1 보급 후, 별도 승인): reporter_ids 컬럼 SELECT 권한 회수.
  **1.0(4) 앱이 이 컬럼을 읽고 있으므로 1단계와 동시에 회수하지 말 것.** 마이그레이션 파일만 준비해 둘 것

### B5. 빌드 준비
- 버전 1.0.1, 빌드 번호는 내가 로컬에서 지정 (project.pbxproj 커밋 금지)
- 빌드 순서: npm run build → npx cap sync ios → 버전·빌드 번호 → Xcode 아카이브 → 업로드 (내가 수행)
